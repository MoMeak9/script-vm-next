# 为什么“能跑 demo”不等于“语义已经正确”？

## 本章目标

做到这里，最小教程版 ScriptVM 已经具备编译、发射、执行的主链路。但要让系统继续演进，必须建立验证方法。读完以后，你应该能回答：

1. 对 ScriptVM 来说，什么才算真正的正确？
2. 为什么不能只靠 AST、IR 或字节码快照做主验证？
3. 测试应该怎样分层，才能既稳又便于定位？
4. 当结果出错时，应该怎样区分“编译错了”还是“运行时错了”？

---

## 先看地图：验证链路要覆盖整条编译执行流水线

```mermaid
flowchart LR
    A["Source"] --> B["AST"]
    B --> C["IR"]
    C --> D["Bytecode"]
    D --> E["Runtime Result"]
    E --> F["与原生 JS 行为对比"]
```

这张图强调的是：J​​SVM 的正确性，最终要落在“行为是否一致”上，而不是落在某个中间产物是否看起来工整。

> 对 VM 项目来说，最可靠的判断标准始终是“同一段源码，原生执行与 VM 执行是否得到同样的语义结果”。

---

## 为什么不能只盯着中间产物

中间产物当然有价值，但它们更适合辅助定位，而不适合作为唯一结论。

| 验证对象 | 适合作什么 | 不适合作什么 |
|----------|------------|--------------|
| AST | 确认解析与预处理是否正确 | 证明最终语义完全正确 |
| IR | 检查 lowering 是否按预期拆步 | 代替端到端行为验证 |
| Bytecode | 检查编码与 fixup 是否对齐 | 单独证明运行时没有 bug |

原因很简单：

- IR 变了，不一定意味着结果变了。
- 字节码看起来对，不一定意味着 `pc` 推进正确。
- 运行结果偶尔对，也不一定意味着语义模型稳固。

所以更合理的策略是：**结果一致性测试做主线，中间层观测做辅助。**

---

## 教程版最重要的测试入口是什么

教程第六步对应的示例文件是：

- `docs/examples/tutorial-jsvm/06-test-your-mini-jsvm.js`

它的核心入口沿用了第四章已经打通的主链路：

```js
function compileAndRunSource(source, globalObject = {}) {
  const ir = compileSourceToIR(source)
  const program = emitBytecode(ir)
  run(program, globalObject)
  return globalObject.__result
}
```

这段函数很重要，因为它说明测试走的是“真实流水线”，而不是绕开编译器去手工喂数据。

---

## 为什么黑盒语义测试应该放在最前面

在教程版里，最先建立的测试习惯是：

1. 写一段源码。
2. 通过完整编译链执行。
3. 断言最终结果。

例如：

```js
function testArithmeticAndIf() {
  const result = compileAndRunSource(`
var x = 40 + 2;
if (x > 20) {
  __result = x;
} else {
  __result = 0;
}
`)

  assert.equal(result, 42)
}
```

这种测试方式的价值在于，它离真实使用方式最近，也最能验证多层组合后是否仍然正确。

---

## 一套更稳的测试分层应该长什么样

### 第一层：结果一致性测试

这是主干。优先覆盖：

- 表达式求值
- 变量初始化与赋值
- 分支与循环
- 闭包
- `this` / `arguments`

### 第二层：关键中间层断点

这是辅助层。只保留少量高价值观测：

- 某段源码是否生成了预期的 `label + jump`
- 某条跳转是否被正确回填
- 某个绑定是否被分配到正确 slot

### 第三层：问题复现用例

每修掉一个 bug，就把触发它的源码留下来，形成回归样例。

这样设计的好处是：

| 分层 | 目标 |
|------|------|
| 黑盒结果测试 | 证明语义行为 |
| 中间层观测 | 缩小排查范围 |
| 回归样例 | 防止以后改动重新引入问题 |

---

## 当结果出错时，怎样定位更高效

可以把排查顺序固定成一条流水线：

```mermaid
flowchart LR
    A["结果不对"] --> B["先看 IR 是否合理"]
    B --> C["再看字节码编码与 fixup"]
    C --> D["最后看 runtime 的 pc / regs / env"]
```

这条顺序的逻辑是：

1. 如果 IR 就错了，问题在 lowering。
2. 如果 IR 对而字节码错，问题在 emit。
3. 如果字节码对而结果错，问题通常在 runtime 状态推进。

这样定位比“直接盯着最终错误猜原因”更稳定。

---

## 为什么最值得保留的是状态型调试信息

VM 最难排查的问题，往往不是抛异常，而是状态悄悄跑偏。因此最有价值的调试信息通常是：

| 调试信息 | 价值 |
|----------|------|
| 当前 `pc` | 判断是否跳到了错误位置 |
| 当前 `op` 与操作数 | 判断读写规则是否对齐 |
| `regs` 快照 | 判断中间结果有没有被覆盖 |
| `env.values` 快照 | 判断变量绑定是否落在正确环境 |

如果只能保留少量调试输出，优先保留这些状态，而不是大段字符串日志。

## 教程第六步真正补上的，不是语言功能，而是工程闭环

`06-test-your-mini-jsvm.js` 这份文件很短，但它把前面五章做出来的能力正式收成了三类回归：

1. 基础算术与 `if`
2. 闭包捕获环境
3. `this` 与 `arguments`

这意味着教程版系统第一次具备了“修改之后能自动回头验证”的能力。对编译器和 VM 项目来说，这层能力并不是附属品，而是能否继续扩语义、扩 opcode、扩优化的基础。

---

## 本章小结

这一章真正要建立的是“验证观”：

- 正确性的最终标准是行为一致，而不是中间产物好看。
- 黑盒结果测试应当作为主验证方式。
- IR、字节码与运行时状态更适合作为排查辅助。
- 一旦形成回归用例，系统就从“实验品”变成了可持续演进的工程。

至此，教程版最小 ScriptVM 已经完成了一次完整闭环：从源码、到 IR、到字节码、到运行时、到测试验证。接下来如果继续扩展语法与语义，新增能力就有了稳定的落点。
