## 推进顺序

2026-10-28 的仓库内验证：Node.js 24.19.0，安装 `0.2.0-beta.1` tarball；`auto`/`full` 各通过 5 组计价、4 组异常及 1 次 CLI 本地模块打包执行。该案例已纳入 `pnpm test:package`，后续 CI 会随安装包验收重跑。此记录不是 npm 发布或外部复测证明。

1. 已按维护者选择补齐 Apache-2.0 `LICENSE`、`NOTICE` 与包元数据；保留第三方许可证。发布时检查 tarball 中的授权文件。
2. 按[发布指南](releasing.md)完成验证，以 `beta` dist-tag 发布并核对明确版本、完整性与干净安装；发布前不要将注册表安装写成已可用。
3. 邀请真实项目维护者尝试独立业务模块，先对比原生与 VM 行为，再逐步扩大输入范围。记录失败、限制和性能开销，不只展示成功截图。
4. 取得报告者同意后收录可核实案例，链接公开 issue、复现代码和已测试版本。发布修复后请原报告者复测；未复测时保持“待外部确认”。

## 如何反馈

在 [GitHub Issues](https://github.com/MoMeak9/script-vm-next/issues/new/choose) 选择“Beta 集成反馈”。提供明确包版本与来源（npm/tarball/提交）、Node 或浏览器版本、操作系统、打包工具、API/CLI 入口、输出格式与运行时模式。附可运行的最小脱敏输入、原生预期、VM 实际行为和复现命令。

性能反馈请分别记录编译耗时、产物字节数与执行耗时，并说明输入规模、重复次数及原生基线。单次耗时或不同环境的数字不能直接作为性能结论。请勿上传密钥、真实订单、客户数据或无权公开的源码；可以用保持同一失败行为的合成数据替换。

## 外部案例收录规则

收录时记录：项目公开链接、报告者与公开授权范围、使用场景、确切版本或提交、宿主与工具链、安装及复现命令、通过与失败的检查、已知限制、反馈 issue 和最后复测日期。分别标注“外部报告，未复现”“维护者已复现”“修复后待外部复测”或“外部已复测”。只有经用户明确允许公开的项目名称、描述及评价才可引用，不将试用反馈改写为生产背书。

目前外部案例列表为空；收到可核实证据后再新增记录。
